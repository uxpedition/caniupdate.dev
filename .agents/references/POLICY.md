# Skill policy

## Policy and precedence

These rules govern every skill that points to this reference set:

- **Runtime and repository portability:** examples are patterns, not commands to run blindly. First inspect the repository's actual framework, project/workspace boundary, package manager and lockfile, configured scripts, CI, documentation destinations, authorization boundaries, and available runtime tools. Use the available runtime's file, shell, browser, and delegation capabilities; when a capability is absent, perform the equivalent directly or state the precise limitation. No assumed slash-command, persona, plugin, hook, browser-MCP, or specific tool-name workflow is part of this repository's contract.
- **Discussion and authorization:** present independent, dependency-ready interview questions together; defer questions whose answers depend on earlier answers. For interview work, use `grilling`: surface the confidence hypothesis, preserve batches of ready questions, and keep the interview's terminal turn as an explicit authorization gate. Before acting on a discussion, require a concrete restatement of the agreed request and an explicit `yes`; phrases such as “sounds good,” “sure,” or delegation alone are not approval. A wrapper must preserve the interview's question batches and terminal gate. Discussion does not authorize implementation or publication automatically. At every interactive doubt cycle, offer cross-model review; obtain explicit authorization for each external CLI invocation used for that cross-model review, not blanket approval for a series. Ordinary repository test, build, documentation, and verification tools follow the runtime's and repository's normal permission policy.
- **Working artifacts:** AI-generated intent/idea briefs, specs, plans, task checklists, and design/execution material are temporary working artifacts, never repository deliverables. Create one uniquely named per-work directory called `workDir` under the operating system's temporary directory, outside the repository. Discover the OS temp location using the current environment/runtime; do not assume one fixed path. The standard paths are `${workDir}/intent.md`, `${workDir}/idea.md`, `${workDir}/spec.md`, `${workDir}/plan.md`, `${workDir}/todo.md`, and `${workDir}/handoff.md`; add module-specific spec files only when needed. Report and propagate the exact absolute `workDir` path through every skill and session that needs it. Temporary specs and plans may cache executable commands and context needed to avoid rediscovery, but remain outside the repository and are never committed. Never guess which spec or plan is active. A POSIX shell example, when that runtime is available, is `mktemp -d "${TMPDIR:-/tmp}/agent-work-<work-id>-XXXXXX"`; otherwise use the platform's equivalent.
- **Durable knowledge:** important current-system, operational, or design decisions belong in the maintained documentation location the repository actually uses, and require authorization before writing. Use an ADR when a decision is costly to reverse; do not require both surprisingness and a genuine tradeoff as joint prerequisites. Do not turn execution logs or temporary specs into durable documentation.
- **Decision quality and constraints:** `package.json` owns quality-gate entry points; tool configuration owns rules and thresholds. Follow [constraint-driven-development](../skills/constraint-driven-development/SKILL.md) to inspect enforcement and report gaps. Documentation explains the configured gates rather than overrides them; changes to enforcement require authorization.
- **Specialist routes:** interview work uses the local `grilling` skill. Use local specialist skills for design and domain vocabulary, including `codebase-design` and `domain-modeling`. Skill references are local pointers.
- **Verification and delivery:** discover the project's applicable checks and exercise the changed behavior at runtime when the environment permits. Tests are evidence for their assertions, not a substitute for observing the changed path. Work safely in small slices and commit each completed slice through the repository's established workflow; commits may contain code and durable documentation only, never temporary working artifacts. Update the appropriate maintained documentation when the durable behavior or public contract changes. Apply the repo's approval and publication boundaries before merging, releasing, or deploying.

## Adapting examples

The checklists cover technical thresholds, threat controls, telemetry guidance, performance diagnostics, test examples, and orchestration tradeoffs. Treat technology-specific syntax, commands, browser menus, and numeric targets as scoped guidance: verify they apply to the current product, version, runtime, users, and SLO before adopting them. Use the repository's configured toolchain and official documentation for its pinned versions; do not silently replace one ecosystem's command with another's. For repository quality gates, use package scripts and the configuration of the enforcing tool.
