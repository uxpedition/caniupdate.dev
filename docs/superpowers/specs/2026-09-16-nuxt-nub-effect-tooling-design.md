# Nuxt, Nub, Effect, and Ox Tooling Setup

**Date:** 2026-09-16
**Status:** Approved design; implementation pending

## Goal

Replace the current Nub TypeScript hello-world starter with a minimal Nuxt application that uses Nub for package management, the latest Effect v4 release candidate for server-side functional composition, and the TypeScript, Oxlint, and Oxfmt policies used by `../docpenny`.

## Constraints

- Work in the current checkout; no linked worktree is required.
- Use Nub (`nub@0.8.3`) for initialization, dependency management, scripts, and the committed lockfile.
- Use the latest published `effect@rc` release, currently `4.0.0-rc.115`; resolve all other packages at their latest available versions.
- Use `@typescript/typescript6` through the `typescript` npm alias because the latest `vue-tsc` cannot load TypeScript 7's removed `typescript/lib/tsc` export; this is the narrow compatibility exception.
- Include the latest `oxlint-tsgolint` bridge required by Oxlint's type-aware mode.
- Use the current Nuxi initializer through Nub with `--packageManager=nub`.
- Keep the existing project name, `can-i-npm-update`.
- Do not introduce pnpm workspace files or pnpm-specific scripts.
- Do not overwrite Nuxt's generated TypeScript project-reference structure.
- Copy `../docpenny` compiler, Oxlint, and Oxfmt policy where it is compatible with Nuxt; remove only irrelevant workspace-specific ignore paths.

## Approaches considered

### Recommended: Nub-driven Nuxi scaffold

Run Nuxi through `nub dlx`, install the resulting dependencies with Nub, and keep Nuxt's generated `.nuxt/tsconfig.*` project references. Put shared compiler overrides in `nuxt.config.ts`, where Nuxt supports them. Add one small Effect-backed server endpoint as a runtime integration proof.

This minimizes divergence from Nuxt's supported project layout while retaining the requested tooling policy.

### Hand-built Nuxt baseline

Create the manifest, Nuxt configuration, app files, and lockfile manually. This gives direct control but duplicates the Nuxi scaffold contract and risks missing generated aliases or required scripts.

### Verbatim `docpenny` configuration transplant

Copy `docpenny` configuration files without adaptation. This carries Svelte/workspace-specific ignore paths and can override Nuxt's generated TypeScript contexts incorrectly, so it is rejected.

## Architecture

The repository becomes one root Nuxt application:

- **Nuxt application:** generated by Nuxi in the repository root.
- **Runtime dependency:** the latest `effect@rc` v4 release is used by a single `server/api/health.get.ts` route.
- **TypeScript:** Nuxt owns root project references and generated context files. `nuxt.config.ts` supplies compatible `docpenny` compiler checks through `typescript.tsConfig` and context-specific overrides only where Nuxt permits them.
- **Linting:** `.oxlintrc.json` retains `docpenny`'s TypeScript/import/unicorn plugins, type-aware mode, and rules; Nuxt-generated output is ignored.
- **Formatting:** `.oxfmtrc.json` retains `docpenny`'s import sorting, 120-column width, semicolon, trailing-comma, and quote rules.
- **Commands:** `package.json` exposes Nub-runnable Nuxt, type-check, lint, and format scripts.

## Runtime proof

`server/api/health.get.ts` will execute a successful Effect program and return a stable JSON response:

```ts
import { Effect } from 'effect';

export default defineEventHandler(() => Effect.runSync(Effect.succeed({ status: 'ok' as const })));
```

This is intentionally not product behavior. It proves that the Nuxt server runtime can import and execute Effect without adding an application abstraction prematurely.

## TypeScript policy

Copy the meaningful `docpenny` compiler checks:

- `target: es2024`
- strict checking
- `skipLibCheck`
- `isolatedModules`
- `esModuleInterop`
- `resolveJsonModule`
- `moduleDetection: force`
- `allowImportingTsExtensions`
- `verbatimModuleSyntax`
- `noUncheckedSideEffectImports`
- `noUncheckedIndexedAccess`
- `exactOptionalPropertyTypes`
- `noEmit`

Nuxt-managed `module`, `moduleResolution`, `types`, `paths`, and per-context `noEmit` settings remain under Nuxt control unless a generated-context override is required and verified. The root `tsconfig.json` remains the Nuxt project-reference file rather than a copied standalone compiler configuration.

## Ox policy

`.oxlintrc.json` copies the following from `../docpenny`:

- `typescript`, `import`, and `unicorn` plugins.
- type-aware analysis.
- unused-variable handling with underscore exemptions.
- TypeScript assertion and safety rules.
- complexity, max-lines, max-lines-per-function, and max-statements limits.
- test-file and JavaScript-file overrides.

Ignore entries that refer only to `docpenny`'s `qa` and package-template directories. Ignore Nuxt-generated and dependency directories instead.

`.oxfmtrc.json` copies `docpenny`'s formatter settings, ignores Nuxt output and `docs/superpowers` planning documents, and retains hidden/generated-output ignores appropriate to this application.

## Files and responsibilities

- `package.json`: Nuxt/Nub dependencies and project scripts.
- `nub.lock`: Nub-resolved dependency graph.
- `nuxt.config.ts`: Nuxt configuration and TypeScript policy overrides.
- `tsconfig.json`: Nuxt-generated project-reference entrypoint.
- `app/app.vue` and generated starter files: minimal Nuxt surface from Nuxi.
- `server/api/health.get.ts`: Effect runtime smoke endpoint.
- `.oxlintrc.json`: copied/adapted Oxlint rules.
- `.oxfmtrc.json`: copied/adapted Oxfmt rules.
- `.gitignore`: Nuxt outputs, dependencies, local environment files, and existing local inspiration exclusion.
- `index.ts`: removed because the Nub hello-world entrypoint is obsolete after the Nuxt cutover.

## Verification

Run the real project paths, not only static configuration checks:

1. `nub install` or the equivalent generated install completes from `nub.lock`.
2. `nub run prepare` generates Nuxt's type contexts.
3. `nub run type-check` passes.
4. `nub run lint:check` passes.
5. `nub run format:check` passes.
6. `nub run --node build` passes without Nub's worker-runtime augmentation errors.
7. Start Nuxt with `nub run --node dev` (Nub package execution with runtime augmentation disabled), request `/api/health`, and observe `{ "status": "ok" }`.

If an exact `docpenny` compiler flag conflicts with Nuxt's generated context, preserve Nuxt's required setting and document the verified adaptation rather than breaking aliases or server/client resolution.

## Out of scope

- Product comparison UI or npm registry behavior.
- Effect services, layers, schemas, or domain abstractions beyond the smoke endpoint.
- Nuxt modules, CSS frameworks, deployment adapters, testing frameworks, or CI changes.
- Copying source code from `docpenny` or `npmx.dev`.
