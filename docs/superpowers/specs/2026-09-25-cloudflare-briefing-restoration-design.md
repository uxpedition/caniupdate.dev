# Cloudflare briefing restoration design

**Date:** 2026-09-25

**Status:** Design approved in discussion; written-spec review pending. No implementation or deployment approved by this document.

## Goal and constraints

Restore useful AI briefings on Cloudflare Workers Free without coupling generation to a browser connection. Keep declarations and measurements independent of AI. Do not upgrade Cloudflare billing, add an application-level daily AI budget, or publish a generation endpoint without a configured OpenRouter key budget. The user controls provider spend through that key budget; it is not an exactly-once billing guarantee.

This design revises the later milestones in [the 2026-09-22 migration design](2026-09-22-cloudflare-briefing-migration-design.md): generation runs in a SQLite-backed job Durable Object, **not** in the Queue consumer; there is **no application budget Durable Object**; pending clients use **hibernating WebSockets**, not SSE or browser polling. The deployed private package-evidence Worker and existing D1 result table remain in use. The earlier document's M1 history and resource/security constraints remain relevant, but its M2/M3 topology and budget requirements are superseded here.

The deployed preview currently returns HTTP 200 with `briefing.reason: 'not-configured'`; this is not a missing route. `server/api/package/[packageName]/compare/briefing.get.ts` obtains a bounded packet from `PACKAGE_EVIDENCE`, then `server/utils/packageBriefing.ts` reads D1 and checks environment configuration before generating. No AI credential was installed in preview. Do not enable paid inference by merely adding a secret to the existing synchronous GET.

Cloudflare documents [10 ms CPU per ordinary Free Worker request](https://developers.cloudflare.com/workers/platform/limits/#cpu-time), [30 seconds per SQLite-backed Durable Object request](https://developers.cloudflare.com/durable-objects/platform/limits/), and Free availability for [Queues](https://developers.cloudflare.com/queues/platform/pricing/) and [SQLite-backed objects](https://developers.cloudflare.com/durable-objects/platform/pricing/). The handoff records preview briefing frontend CPU samples of 59/68 ms with AI disabled, and an evidence object sample of 352 ms. Successful individual over-limit frontend requests do not prove sustained Free-tier viability. The ordinary Nuxt Worker and Queue consumer must each meet their own Free limits; moving AI to a DO does not fix frontend CPU automatically.

## Request and result contract

1. The browser waits for declarations to resolve exact versions, then submits the package/version pair client-side. Nuxt validates the same inputs as the existing route and requests the exact bounded packet from the private evidence object. Reuse the evidence object's persisted archive and five-minute mutable-provider evidence according to its existing policy; a new snapshot may differ after refresh. Never accept browser-supplied facts or hashes.
2. Identify the snapshot by the existing SHA-256 of `JSON.stringify` of the schema-decoded, bounded, model-visible evidence. Preserve byte-for-byte identity and serialization ordering across the migration: D1 results already paid for must remain hits. Validate the packet and its hash again at the job boundary. Retrieval timestamps, model, provider key, and prompt do not enter the hash.
3. Submit that packet through a **private service binding** to the briefing service. A job Durable Object addressed by the hash checks `BRIEFINGS_DB` before configuration or dispatch. Return the validated stored result immediately on a hit. On a miss, concurrent submissions for that hash join one active generation; the object persists the immutable packet and queued generation state before returning `202` with the hash and WebSocket URL. Fail closed if D1 cannot be read or the job cannot be durably recorded.
4. The Queue carries only hash and generation identifier, not the evidence packet or credentials. Its small Free-tier consumer forwards the message to the job object and acknowledges only after the object reports a durable terminal or already-owned state. The job object performs provider generation, response validation, D1 storage, and notification. The provider uses the saved packet, not freshly collected evidence.
5. The existing successful `package_briefings` row is permanent, first-writer-wins, and the authority for available results. The job object writes the validated success, reads back the canonical row, commits `available`, and only then tells subscribers. Unavailable attempts are **not** stored as successful D1 briefings. Changed evidence creates a different job/hash; reverting to old evidence can reuse its old D1 row.

The new browser-facing submission endpoint is `POST /api/package/{encodedPackageName}/compare/briefing?from=...&to=...`. It returns `200` with the existing `{ packageName, from, to, briefing }` available envelope on a D1 hit, or `202` with resolved versions, job hash, `queued`/`running` state, and subscription URL. A missing binding, malformed evidence, or D1 outage is an explicit sanitized non-success response, not a fictitious queued job. The client-only Vue Query flow renders available immediately or waits for the job; declarations and measurements never wait for it. During cutover, migrate every caller and remove the old synchronous-generation GET, rather than retaining a bypass around coordination.

## Delivery

The preview site remains `can-i-update-preview.caniupdate-dev.workers.dev`. A separate briefing-service Worker under its own `workers.dev` hostname exposes **only** the read-only `GET /api/briefings/{hash}/events` WebSocket upgrade to browsers. Internal submission, dispatch, and provider controls are reachable by binding, not via public fetch routes. Accept browser upgrades only from the preview site's exact Origin; reject other methods and unexpected paths. Do not expose the packet, provider configuration, or raw provider errors to subscribers. The service must not require a paid custom domain.

The job object uses Cloudflare's WebSocket Hibernation API. On subscription, reconcile D1 before sending the current durable state/revision; a success written before a crash or before the browser connects must not remain stuck behind an old `running` state. On `available`, send the canonical briefing including citations and close the socket; on `unavailable`, send a sanitized reason and close it. Ignore duplicate/stale revisions. A browser reconnect reads current state; it never submits or pays for another generation. Changing comparisons closes the old socket and ignores old messages without canceling shared work. There is no browser polling, SSE stream, invented progress percentage, or WebSocket command that creates/retries work. Verify actual cross-hostname upgrade/Origin behavior in local workerd and isolated preview.

## Failure and retry rules

The job object persistently tracks `queued`, `running`, `available`, and `unavailable` plus generation ID, dispatch status, and a lease/fencing token. It schedules a recovery alarm before acknowledging a queued job; a missed Queue send/ack can be retried while generation has **not** started. Queue deliveries are at least once; duplicates for the same generation observe the stored state and must not call OpenRouter again. Once a provider request begins, a process loss or ambiguous timeout is not automatically re-spent: after lease expiry reconcile D1; if no success was stored, mark that attempt unavailable and notify subscribers. A new explicit POST after failure may create a fresh generation for that hash, subject to the OpenRouter key budget. Reconnecting sockets and status reads never do this.

Preserve the existing provider URL/secret/redirect/response-size checks, prompt, evidence/citation validation, 75-second total generation deadline, and **one retry only for invalid output** within that deadline. If both outputs are invalid, or the provider fails, publish a terminal unavailable event; store no briefing in D1. No automatic retry on provider HTTP/transport failure or timeout. A D1 write failure after generation also publishes unavailable; it may already have consumed provider budget. Queue delivery failures and exhausted recovery must not leave a job indefinitely reported as `queued`. Keep the previous generation's terminal state available to connected subscribers until a new explicit submission supersedes it; it is not a cached success. Delete the saved evidence packet after a terminal state; a later POST obtains the then-current packet from the evidence object, so job metadata cannot accumulate permanent 48 KiB packets per hash.

Configure OpenRouter endpoint/model and its capped API key as server-only secrets **on the briefing service**, not the evidence Worker or browser. Reuse the current provider and store implementations by migrating their caller/configuration boundary, not copying the inference pipeline. Preserve provider response sanitization; never log tokens, raw provider bodies, or full packets. The application does not implement a second spending counter or daily cap. The key cap limits total provider spend, but cannot guarantee one bill per job when the provider accepts a call and the worker dies before recording its result.

## Implementation and rollout gates

1. Establish an isolated local `workerd` baseline for the built preview and profile Nuxt request CPU separately from evidence-object CPU. Run the same briefing submission path with a fixture provider; assess whether removing inference/D1 work from Nuxt brings the **ordinary Worker** within Free's 10 ms CPU limit. If not, move only observed hotspots into the service/object boundary and repeat. Do not claim Free readiness from a single successful over-limit response.
2. Implement the job-object persistence/dispatch/provider lifecycle with bounded packet and existing hash/D1 identity. Use a fixture OpenAI-compatible provider, never a real paid key, for automated and local runtime verification. Cover two concurrent submissions, duplicate Queue deliveries, restart between enqueue and dispatch, browser disconnect, provider invalid-output retry and second failure, provider transport failure, D1 read/write failure, and crash after D1 success before notification. Verify a new POST retries an unavailable attempt while a socket reconnect does not.
3. Cut over API, client, and WebSocket routing together. In real local `workerd`, exercise initial-state-on-connect, success before subscription, reconnect after object restart, multiple subscribers, stale comparison navigation, and Firefox/Chromium search-to-comparison and direct reload. Preserve factual routes and evidence citations. Update README, environment example, and deployment commands; remove obsolete synchronous-generation route/configuration and tests that pin its old behavior.
4. A remote preview deployment, new resources, and attaching a real OpenRouter key each require separate explicit approval. Before public inference, configure the provider key budget, deploy backend before the frontend binding, and measure repeated/concurrent request CPU, DO duration/storage, Queue operations, D1 reads, outcomes, and actual browser flow. Free quotas and failure outcomes are exit gates; if sustained ordinary-Worker CPU remains over 10 ms or another Free resource limit is exceeded, stop rollout. Do not silently upgrade billing, weaken evidence checks, or return to uncapped synchronous GET.
